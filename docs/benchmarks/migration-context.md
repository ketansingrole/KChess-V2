# TypeScript to Rust study: comparison context

## Revisions and interpretation

The TypeScript endpoint is `f479f7ce10d7363df7132d616d8ad71b775ec7a7` (the extracted source is `/private/tmp/kchess-benchmark-ts`). The Rust endpoint is `8f58da7f4d51371001e95d1c33cbd51ed9ad20c2`. The first Rust migration commit is `8f5b7ddcd2b02724d80d8d94c69d33ec61dd3780`, “Move the core's chess and document rules to Rust.” The endpoints therefore bracket the migration and the subsequent integration/packaging work; they are not a one-commit language-only experiment. The baseline is the last TypeScript-only revision selected before that first Rust migration, while the extracted copy keeps baseline builds and measurements separate from the current checkout.

Treat results as an end-to-end comparison of these two application revisions. A task-level difference can include the implementation language, changed algorithms/data representation, work moved between processes, and integration changes. It does not by itself estimate a general TypeScript-versus-Rust effect.

## Runtime paths that changed

- The old desktop main process called the TypeScript core package (`core/src/services`); the new main process uses the `@kchess/native` package and its Rust core through N-API. The Node binding accepts a JSON argument array and returns a JSON result (`crates/kchess-node/src/core.rs:86-110`; adapter `crates/kchess-node/js/nativeCore.ts:108-119`). In the desktop, renderer-to-main Electron IPC still exists, so desktop core calls now include the IPC boundary plus JSON conversion at the N-API boundary. This can affect small/frequent calls and large payloads independently of Rust execution speed.
- Chess/domain and document rules have moved into Rust for the Node core. Shared rule-facing TypeScript remains in `crates/kchess-wasm/js`; the renderer binds those rules to WebAssembly while the native core binds them to Rust. Renderer-only rule-heavy tasks therefore exercise WASM/shared code, not the native Node addon, and must not be presented as measuring Rust core throughput.
- Storage and service ownership also changed. The Rust core owns the main profile database, puzzle database, network/service state and engine lifecycle. That changes host crossings, async scheduling, initialization, and the number/location of worker or process boundaries in addition to replacing TypeScript code.
- The app remains an Electron + Nuxt/Vue/Pinia desktop app. In both revisions the direct manifest/lock versions for Electron, Nuxt, Vue, Vite and Stockfish are the same (`electron` 44.5.1, `nuxt` 4.6.0, `vue` 3.5.43, `vite` 7.3.6 and `stockfish` 19.0.0 in the available install). The UI and app code did evolve during the migration, so equal framework versions do not guarantee equal rendering work or feature paths.

## Caches, concurrency, and crossings

- Profile and rating reads keep the same five-minute, 100-entry in-memory policy plus the persisted `api_cache` fallback in both endpoints. The baseline uses `lru-cache`'s `fetch`, which coalesces concurrent misses for one key (`core/src/services/lichess.ts:143-164,2009-2022`). Rust checks a bounded in-memory map and releases its mutex before fetching, then stores the completed result (`crates/kchess-core/src/lichess/accounts.rs:501-575`). Sequential warm behavior is comparable; simultaneous cold misses can issue duplicate requests in Rust. The loopback benchmark measures sequential calls and does not cover that difference. Presence checks have a similar change: both retain up to 100 results for 4 seconds, but the TS `LRUCache.get` returns an in-flight promise while Rust caches only completed reports, so concurrent cache misses may duplicate requests there as well (`core/src/services/lichess.ts:1824-1840`; `crates/kchess-core/src/lichess/online.rs:2075-2097`).
- Per-account game syncs still join an in-flight sync in both revisions. Engine search scheduling also preserves a one-active-lease priority queue: computer moves outrank analysis, which outranks review; a higher-priority request stops the active search, and search threads are capped to four (two on battery). The TypeScript scheduler lives in `core/src/services/engineScheduler.ts`; Rust uses `crates/kchess-core/src/engine/scheduler.rs`. Both derive a CPU budget by subtracting one logical CPU, but use different host APIs (`os.cpus().length` and `available_parallelism`), so actual counts can differ on some hosts.
- Renderer-to-main Electron IPC remains the desktop crossing. The Rust implementation then serializes method arguments to JSON for the N-API call, parses them as `serde_json::Value`, dispatches inside Rust, serializes the result, and parses it back in JavaScript (`crates/kchess-node/js/nativeCore.ts:108-119`, `crates/kchess-node/src/core.rs:86-110`). These crossings make bridge-inclusive measurements materially different from isolated Rust code timing. The core runs headless and uses `CorePlatform` for host capabilities rather than importing Electron.
- Main-profile `api_cache` keys and payload shape remain persisted in the same SQLite table. The table stores JSON values and `fetchedAt`; cache eviction/invalidation flows moved to Rust storage code. Identical TTLs and PRAGMAs do not imply identical concurrent request behavior or conversion costs. The endpoint lockfiles are not identical: for example, Nuxt 4.6.0’s dependency closure resolves Acorn 8.18.0 in the TypeScript lock and 8.19.0 in the Rust endpoint lock. The direct Electron/Nuxt/Vue/Vite/Stockfish versions match, but the full dependency graph did not stay fixed.

## Engine and storage controls

Stockfish itself is not the Rust chess engine. Both revisions use Stockfish 19's bundled lite, multithreaded WebAssembly build (`node_modules/stockfish/bin/stockfish-19-lite.js` plus its `.wasm`), launched as a child Node process; a user-selected or managed native Stockfish binary can take precedence. The Rust core now owns UCI process handling, deadlines, scheduling and cancellation (`crates/kchess-node/js/engine.ts:1-7`; `crates/kchess-core/src/engine/uci.rs`). Search speed is still principally Stockfish speed and search configuration. A game/search benchmark also includes changed UCI orchestration and lifecycle code, and should not be described as Rust replacing Stockfish.

The main `kchess.db` connection uses the same PRAGMAs on both sides: WAL, foreign keys on, synchronous NORMAL, in-memory temp store, and a 20 MiB SQLite page cache, followed by migrations and restrictive file permissions. See baseline `core/src/services/db.ts:12-27` and Rust `crates/kchess-core/src/store/mod.rs:92-105`. Puzzle storage likewise retains WAL and synchronous NORMAL; the Rust schema comment explicitly preserves the old worker's schema/PRAGMA order (`crates/kchess-core/src/puzzles/queries.rs:114-123`). The SQLite implementation boundary did change: the old code used Node's built-in `node:sqlite`; Rust uses bundled `rusqlite` (`crates/kchess-core/Cargo.toml`). Identical SQL and PRAGMAs do not imply identical SQLite library builds, locking/scheduling, or call overhead.

## Confounders to retain beside measurements

- The Rust endpoint includes continued feature work and refactors after the initial port. UI edits, service semantics, cache keys/lifetimes, concurrency limits and payload shapes can change measured task cost. Attribute improvements only to the observed endpoint unless a microbenchmark isolates the language implementation with equivalent inputs and outputs.
- The N-API bridge encodes arguments with `JSON.stringify`, parses them into `serde_json::Value`, executes a method, serializes its result, and parses it back in JavaScript. This is material for high-frequency small calls and large documents. Measure bridge-inclusive latency separately from an in-Rust operation before drawing conclusions about compute-heavy rules.
- Rust startup includes loading a platform-specific native addon and constructing the Rust core/runtime; the old endpoint loaded JS modules and lazily initialized TypeScript services. First-run migrations, profile state, engine warm-up, voice model availability and OS file-cache state can dominate startup. Report cold and warm runs separately and use equivalent profile/database state.
- Package-size changes are not a clean Rust-size measurement. The Rust app adds a compiled `.node` addon (plus shared rules WASM) and excludes a set of former JS runtime dependencies (`fflate`, `lru-cache`, `openapi-fetch`, `tar`, `valibot`, `chessops`, and `@lichess-org/types` were removed from the old package dependency placement). The current desktop packager explicitly includes the addon, omits type/map files, and prunes package sources. The latest endpoint commit also specifically optimizes Windows native-core release package size. Installer/app size compares all these packaging and dependency changes, not just Rust versus TypeScript source size.
- Native addon artifacts are target-specific. Release coverage is macOS arm64, Windows x64, and Linux x64; a result from one host/architecture does not establish performance or package size for the others. Release targets and supported downloads are documented in `AGENTS.md`; `tooling/build-native.mjs` builds for the current platform/architecture.
- The extracted baseline has no Git metadata in its location, so record the expected baseline SHA above with every raw result. The workspace's installed `node_modules` was checked for the shared framework/engine versions listed above; use each revision's lockfile for exact dependency resolution and avoid claiming the entire dependency graph is unchanged. Rust crate versions are pinned separately by `Cargo.lock`.

For every table, state the task and its boundary (UI, IPC/API, storage, rule compute, engine search, startup, or package artifact), host OS/architecture, warm/cold state, fixture/profile state, repetitions and statistic. Comparisons that cross different boundaries should remain separate.
