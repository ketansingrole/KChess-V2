# Performance hotspots: causes, confidence, and next measurements

This is a source-based interpretation of the TypeScript endpoint `f479f7ce10d7363df7132d616d8ad71b775ec7a7` and Rust endpoint `8f58da7f4d51371001e95d1c33cbd51ed9ad20c2`. It complements [the measured study](2026-10-10-typescript-vs-rust.md) and [migration context](migration-context.md). The endpoint comparison includes architecture, dependency, and integration changes; it does not isolate a language effect.

## Where the work crosses boundaries

### Headless core calls

The current TS facade at `crates/kchess-node/js/nativeCore.ts:105-119` JSON-stringifies arguments before calling N-API and parses the returned string. `crates/kchess-node/src/core.rs:54-82` parses that string into `Vec<serde_json::Value>`, dispatches the core method, then serializes the result. This makes core timings include two serialization and parse stages around Rust work. Desktop calls additionally use `ipcRenderer.invoke` (`apps/desktop/electron/preload/index.ts:25-29`) and an owned-frame/argument-validation handler (`apps/desktop/electron/main/ipc.ts:45-85`). A large result such as a 100-row page is therefore a good candidate for payload/bridge profiling, although its observed absolute regression is below 1 ms.

Argument validation at both the main IPC and Rust core boundaries is deliberate defense in depth: IPC must reject bad/untrusted renderer input, while the core remains valid for Node and CLI callers. Rust's facade validates via `kchess_domain::misc::validate_arguments` (`crates/kchess-core/src/facade.rs:305-320`). Avoid removing the second guard for a small-call benchmark; measure its cost and preserve both contracts. If a measured large document makes validation expensive, consider sharing a normalized validated representation within a boundary rather than bypassing validation.

For the 50k-game page workload, a scratch profile decomposed the calls: the baseline reuses filtered totals between writes (`core/src/services/store.ts:481-531`), while Rust's `game_page` runs `COUNT(*)` for every call (`crates/kchess-core/src/store/games.rs:761-814`). Count-only was 0.869 ms TS vs 0.994 ms Rust; page rows alone were 0.104 vs 0.107 ms; count plus rows was 1.006 vs 0.993 ms. The 4.5× warm public-call ratio in the main report therefore mainly reflects a baseline warm-cache advantage. NativeCore async/sync page probes are within about 0.02 ms of the Rust public call, while direct insights API and sync/async probes differ by at most about 4.6 ms on a ~983 ms workload. JSON bridge overhead is not the primary cause in these cases. A count cache is an optional low-priority parity fix; invalidation must remain tied to every game mutation.

The largest repeated-work query hotspot is the insights SQL path. It selects up to 20,000 rows and evaluates two separate SQLite local-time `strftime` expressions for weekday and hour (`crates/kchess-core/src/store/insights.rs:126-154`; baseline `core/src/services/insights.ts:48-77`). In the scratch fixture, the original local-time SQL took 950 ms TS / 974 ms Rust; a combined local-time CTE took 490 / 502 ms and returned exactly the same rows for all fixture records (about 48% faster). A UTC-only diagnostic was about 19–20 ms but returned different buckets for dates around local-time boundaries, so it is not a valid optimization. The combined local-time SQL is the promising change to evaluate; its recorded host zone was Asia/Tokyo. The full core API includes subsequent aggregation and bridging, which is why total insights remains around 1.4 seconds in the separate end-to-end workload.

There is also a distinct high-cardinality aggregation hotspot. Rust's helper `slot()` searches a vector for each opening family (`crates/kchess-core/src/store/insights.rs:78-86,184-190`); the baseline uses `Map.get` (`core/src/services/insights.ts:91-109`). With 20,000 distinct opening-family labels, Rust rose to 1,246 ms while TypeScript measured 992 ms (`n=3`). This is a synthetic stress case, not the normal repeated-opening fixture. An insertion-ordered vector with a hash map of family→slot can keep output order and make lookup expected O(1); preserve exact JSON ordering/parity and add a high-cardinality regression fixture if implemented.

### Renderer rules and analysis tree

`crates/kchess-wasm/js/engine.ts:23-25` serializes the argument list, calls a binding, and parses the JSON response. The WASM adapter (`crates/kchess-wasm/js/engine.ts:112-141`) UTF-8 encodes both method and arguments, allocates wasm buffers, invokes Rust, decodes the output, and frees buffers. The Rust N-API rules path uses the same JSON method/args shape, but through the native addon. At this boundary, one public helper call normally means one rules invocation; its JSON bytes and encoding costs grow with a supplied document/tree.

The tree is owned and walked in TypeScript/Vue so the renderer can preserve reactive node identity. The Rust decision helper intentionally receives only the data needed for a mutation (`crates/kchess-domain/src/trainer/analysis_tree.rs:1-5`): `addMove` finds the parent in JS, then sends path, UCI, parent FEN/ply, and that parent's child UCIs (`crates/kchess-wasm/js/analysisTree.ts:79-94`). It does **not** re-send the whole tree per move. This boundary is already appropriately narrow for board edits.

Full-document paths do move the entire document. `treeFromPgn` returns the nested tree to JS; `treeToPgn` serializes the entire tree argument to Rust and returns the PGN (`analysisTree.ts:142-151`, `crates/kchess-domain/src/api.rs:293-329`). The analysis store computes `documentPgn`, deep-watches its root, and debounces session and study saves (`apps/desktop/app/stores/analysis.ts:63-100, 237-246`; `apps/desktop/app/utils/library.ts:34-79`). Each persisted session includes PGN, path and metadata; the renderer clones command/session values before IPC (`apps/desktop/app/utils/library.ts:49-65`; `apps/desktop/app/stores/studies.ts:24-33`). These are linear in document size by design. For very large studies, the practical question is how many times a user's edit causes full-tree serialization, string copies and deep traversal, not the cost of an individual small `addMovePlan` call.

The WASM binding also calibrates `Math.exp` behavior by making 4,000 WASM `kc_exp` calls during binding creation (`crates/kchess-wasm/js/engine.ts:47-64`). This is a bounded initialization cost and should be included in cold-start measurements, but excluded from warmed per-rule-operation timing. The public timing comparison currently excludes binding initialization. It cannot explain a large steady-state rules difference.

### Startup and memory

The native addon removes JS core/domain implementation from the running headless worker, which is consistent with the measured drop in worker heap and RSS. It adds a native addon to the packaged app; the renderer also carries and instantiates a WASM rules module. The desktop measurement shows the combined app has higher idle and analysis RSS even while the separate headless worker uses less. This is the measured distinction to preserve: a Rust worker-memory win does not establish a whole-app memory win. The current package payload is 31.7% larger while full app logical files are 2.16% larger; these totals reflect the native addon, WASM, dependency pruning and packaging rules together.

## Multi-hundred-ply tree probe

The companion [bridge-hotspots harness](../../tooling/benchmarks/bridge-hotspots.mjs) generates valid 128-, 384- and 768-ply knight-cycle PGNs and runs the public analysis-tree helpers through the historical TS implementation, current WASM implementation, and native rules module. It checks output digests and records JSON UTF-8 byte counts and method-invocation traces for import, PGN serialization, full-depth navigation, and a deep-edit reuse. `--verify` is correctness/size-only; `--measure` batches 20 warm calls in seven alternating fresh-process pairs per candidate. Raw records are [bridge-hotspots-correctness.json](raw/bridge-hotspots-correctness.json) and [bridge-hotspots-timing.json](raw/bridge-hotspots-timing.json).

The output confirms the expected shape: 768-ply import returns about 92.7 KiB of tree JSON; the matching `treeToPgn` request is about 92.8 KiB and its response 5.0 KiB. Import and serialization each use one rules call; navigation and a deep edit each use two (`movesOf` plus `pathOf` or `addMovePlan`). The deep edit's two requests total about 7.8 KiB, and all four request/response strings total about 16.8 KiB; it does not send the full 92.7 KiB tree. Across the 128→768 range, PGN and tree payloads grow near linearly. Output digests match all three implementations. Paired median per-operation timings are:

| Plies | Operation                           | TypeScript |     WASM |   Native |
| ----: | ----------------------------------- | ---------: | -------: | -------: |
|   128 | Import PGN to tree                  |   0.345 ms | 0.160 ms | 0.133 ms |
|   128 | Serialize tree to PGN               |   0.022 ms | 0.125 ms | 0.092 ms |
|   128 | Navigate full path and rebuild path |   0.011 ms | 0.029 ms | 0.020 ms |
|   128 | Deep edit reuse                     |   0.020 ms | 0.027 ms | 0.019 ms |
|   384 | Import PGN to tree                  |   0.997 ms | 0.441 ms | 0.365 ms |
|   384 | Serialize tree to PGN               |   0.039 ms | 0.377 ms | 0.323 ms |
|   384 | Navigate full path and rebuild path |   0.025 ms | 0.073 ms | 0.063 ms |
|   384 | Deep edit reuse                     |   0.034 ms | 0.062 ms | 0.049 ms |
|   768 | Import PGN to tree                  |   1.747 ms | 0.848 ms | 0.745 ms |
|   768 | Serialize tree to PGN               |   0.064 ms | 0.852 ms | 0.772 ms |
|   768 | Navigate full path and rebuild path |   0.051 ms | 0.179 ms | 0.115 ms |

This synthetic linear mainline shows that Rust rules still import these trees faster, while full-tree serialization and navigation pay measurable boundary cost as the document grows. The deep-edit timed loop warms by adding `d2d4` once, then measures reuse of that child at the same deepest path; it captures the path and `addMovePlan` bridge but not a fresh-node insertion on every iteration. Even the 768-ply full serialization remains under 1 ms in this microbenchmark; whether it affects the app depends on Vue traversal, frequency of saves, variations/comments, IPC persistence, and real user hardware. The existing 34-ply equivalent import was 149.72 µs in TS, 62.73 µs in renderer WASM, and 40.29 µs in native N-API; no import regression is demonstrated.

## Practical next steps by measured impact

1. Prototype the exact-result combined-local-time insights query and profile per-row aggregation separately. Validate against a wider timestamp range and multiple system zones before adopting it; the UTC diagnostic is not equivalent.
2. Replace linear opening-family slot lookup with an insertion-ordered vector plus hash index, preserving deterministic order; benchmark the 20k-family stress case and normal low-cardinality data.
3. Profile and reduce idle/analysis renderer and Browser-main memory; it is the clearest measured whole-app resource regression. Measure the WASM instance and retained tree/UI allocations separately before changing ownership or unloading rules.
4. Keep the filtered game-count cache as an optional low-priority parity improvement. Invalidation must cover all game mutations; the row query itself is already at parity and the warm difference is under 1 ms absolute.
5. Use the tree-scaling raw to decide whether large-document save paths need coalescing or cached PGN revisions. The full-tree WASM boundary is measurable but sub-millisecond at 768 plies in this probe; retain the existing 150 ms persistence debounce and do not introduce a cache without edit/recovery parity tests.

Do not add a general cache of serialized mutable trees without measuring invalidation cost and verifying comments, NAGs, variations, session recovery, and interrupted writes. Do not bypass the Rust rules bridge or duplicate chess rules in TypeScript as a latency shortcut.
