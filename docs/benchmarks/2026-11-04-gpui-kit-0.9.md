# GPUI Kit 0.9.0 (GPUI 0.3.11): frame cost and latency against 0.8.0

**Status: complete.** `main` before the upgrade (gpui-kit 0.8.0, GPUI 0.3.9 with
`vendor/gpui-pre-macos`) against the upgrade (gpui-kit 0.9.0, GPUI 0.3.11, no macOS fork).
Release builds with `--features bench`, `cargo xtask bench --runs 3 --seconds 20`, alternating
run by run on an Apple Silicon Mac at 120 Hz; medians. Raw figures:
[`raw/gpui-kit-0.9-2026-11.json`](raw/gpui-kit-0.9-2026-11.json).

| Scenario          | Figure                  | 0.8.0 | 0.9.0 |
| ----------------- | ----------------------- | ----: | ----: |
| `home-idle`       | Process CPU             | 0.1%  | 0.1%  |
|                   | Change to frame p50, ms |  2.03 |  4.12 |
| `local-clock`     | Draw p50, ms            |  2.22 |  1.50 |
|                   | Draw time, ms per s     |  2.15 |  1.74 |
|                   | Change to frame p50, ms |  2.30 |  7.62 |
| `board-animation` | Draw p50, ms            |  1.94 |  1.53 |

|                   | Change to frame p50, ms |  2.32 |  8.80 |
| all three         | Peak resident memory    | 192–211 MiB | 180–197 MiB |

Frames drawn per second are the same in every scenario.

## Why change to frame is slower

`vendor/gpui-pre-macos` (`FrameDemand`, see
[2026-10-30-gpui-frame-cost.md](2026-10-30-gpui-frame-cost.md)) drew a lone change at once,
without the display link. GPUI 0.3.11 rewrote the macOS frame source: on macOS 14+ a
`CAMetalDisplayLink` pauses after a frame that draws nothing and resumes when GPUI asks for a
frame, so an idle window still costs nothing, but a change waits for the next refresh (up to
8.3 ms at 120 Hz). Porting the patch onto the new frame source would mean keeping a fork of
code upstream has just rewritten; one refresh is not visible in the app, so the fork was
dropped. On macOS 12 and 13 GPUI still uses a `CVDisplayLink` that runs while the window is
visible.
