# Insights and game-page hotspot study

These measurements describe the pre-fix endpoint. Subsequent changes and measurements are tracked in [Performance fixes](2026-10-10-performance-fixes.md).

This study isolates likely costs behind the TypeScript-to-Rust comparison. It uses the same 50,000-game SQLite fixture as the core benchmark, with a 60-second timestamp stride, and runs the baseline TypeScript and Rust workers sequentially on the same machine. The detailed timings, signatures, and SQLite query plans are in [`raw/insights-hotspots-2026-10.json`](raw/insights-hotspots-2026-10.json). The harness is [`tooling/benchmarks/insights-hotspots.mjs`](../../tooling/benchmarks/insights-hotspots.mjs).

The machine was an Apple M5 with Node 24.21.0 and host system time zone `Asia/Tokyo`. The original TypeScript/Rust workers explicitly set `TZ=Asia/Tokyo` in [`insights-hotspots.mjs`](../../tooling/benchmarks/insights-hotspots.mjs#L387); only the later dedicated timezone probe includes a worker with `TZ` unset. Each SQL/API probe had seven warm samples per worker, except for the three-sample high-cardinality probe. These are microbenchmarks from one process per implementation, not independent-process confidence intervals. They measure wall time and do not attribute CPU among SQLite, Rust aggregation, serialization, or N-API scheduling.

## Findings

The 20,000-row insights SQL spends most of its time formatting local time twice for every game. The original query's median was 950 ms in TypeScript and 974 ms in Rust. A single `strftime('%w %H', ..., 'localtime')` expression, split into weekday and hour afterward, preserved every returned row and reduced SQL median to 490 ms and 502 ms respectively, about a 48% reduction. An initial CTE variant also preserved fixture output at 490 ms and 497 ms, but its `DISTINCT utcHour, strftime(...)` projection may evaluate `strftime` before deduplication, so it does not establish that formatting was reduced to one call per hour. A new controlled probe tests a distinct-first, materialized CTE separately. UTC-only formatting took 19–20 ms but changed results and is not a behavior-preserving option. Fetching raw timestamps and converting with JavaScript local `Date` methods took 23–24 ms for selection and conversion only; aggregation was not included, so that is not an end-to-end alternative measurement.

The full `insights` API measured 982 ms median for both implementations (Rust 983 ms, TypeScript 982 ms). That closely tracks the original SQL measurement, so the SQL query is the dominant demonstrated cost in this fixture. The experiment did not run the complete API with the proposed combined expression, so the expected end-to-end benefit remains to be measured before implementation.

## Time-zone resolution probe

A focused follow-up ran the same SQL variants in three fresh sequential Node processes: with `TZ` unset (host default), set to `Asia/Tokyo`, and set to the exact `/etc/localtime` target. `Intl` resolved the host zone as `Asia/Tokyo`; the local-time file resolved to `/private/var/db/timezone/tz/2026c.1.0/zoneinfo/Asia/Tokyo`. All three processes produced identical full-row digests for the modern 20,000-row fixture and a 87,696-row grid sampled every 30 minutes from 1948 through 1952, including Tokyo's historical DST interval.

Within this controlled probe, the original two-`strftime` query median was 1,367 ms with host `TZ` unset, 979 ms with the explicit zone name, and 1,155 ms with the explicit file path. Process user/system CPU deltas across all timed variants were 2,218/12,342 ms, 2,277/8,201 ms, and 2,319/9,961 ms respectively. System CPU was about 85% of measured CPU in the default run. The named-zone run therefore had 28% lower original-query wall time and 34% less measured system CPU than the unset run, with nearly unchanged user CPU. This supports repeated host-timezone resolution as a likely major cost. It does not prove that SQLite calls a specific syscall per row; the probe measures process CPU, not syscall counts, and the absolute timings differ from the earlier core-backed SQL microbenchmark.

The distinct-first materialized hour-bucket query took 22.0 ms p50 with the host default, 19.1 ms with the explicit zone name, and 20.4 ms with the explicit file path, versus 1,367/979/1,155 ms for the original query. In this fixture that is over 60 times faster than the original. It matched both tested Tokyo datasets. This remains a zone-specific candidate: converting the start of each UTC hour assumes the local offset is constant and hour-aligned throughout that UTC hour. Fractional-hour zones and transitions inside an hour can change weekday/hour values. The explicit `TZ` setting was confined to benchmark subprocesses and is diagnostic evidence, not a recommendation to change the application process environment.

The Rust `gamePage` median was 0.994 ms versus 0.191 ms in TypeScript on repeated warm calls. The Rust path runs `COUNT(*)` and then fetches page rows on every call in [`games.rs`](../../crates/kchess-core/src/store/games.rs#L761); the baseline at `/private/tmp/kchess-benchmark-ts/core/src/services/store.ts:516` caches totals by filter until games change. Isolated timings show page-row retrieval at 0.107 ms in Rust and 0.104 ms in TypeScript, while the count alone took 0.994 ms and 0.869 ms. The repeated count explains the observed warm-call difference. SQLite uses covering indexes for the count and page index for rows. A filter-keyed count cache with invalidation on every game mutation is the direct candidate; measure invalidation paths and stale-total behavior before adopting it.

The native dispatch mode is not a meaningful hotspot: Rust's direct async store call had a 978 ms median and the synchronous call 983 ms for insights; on `gamePage` they were 0.999 ms and 0.977 ms. Both returned outputs matched the public API. The few-microsecond differences are small relative to the measured work.

A scratch-only high-cardinality probe changed opening labels to 20,000 distinct values. Rust insights rose from 983 ms to 1,246 ms median; TypeScript remained near 992 ms. Rust's `slot` helper in [`insights.rs`](../../crates/kchess-core/src/store/insights.rs#L80) linearly searches a `Vec` for each opening family, while TypeScript uses a `Map`. This confirms a secondary scaling hotspot for data with many distinct opening names. The report returns no opening groups in this probe because each appears once and both implementations filter groups below two games; the internal grouping still processes all distinct labels. Replacing the vector lookup with a hash map while separately preserving the current first-seen ordering is a viable candidate, but should be benchmarked with parity checks before changing production code.

## Scope and limits

The SQL variants ran only against disposable fixture profiles. The combined local-time expression and hour-bucket CTE matched all selected fixture rows in `Asia/Tokyo`; this does not validate unusual historical time-zone transitions or all supported host zones. The UTC diagnostic intentionally differs. The 20,000-opening probe is synthetic and tests cardinality, not a claim about typical user data. No product source was changed.

The query plans and exact samples are preserved in [`raw/insights-hotspots-2026-10.json`](raw/insights-hotspots-2026-10.json) and [`raw/insights-timezone-probe-2026-10.json`](raw/insights-timezone-probe-2026-10.json). The timezone harness is [`tooling/benchmarks/insights-timezone-probe.mjs`](../../tooling/benchmarks/insights-timezone-probe.mjs). Source-level hotspots are the two `strftime` calls in [`insights.rs`](../../crates/kchess-core/src/store/insights.rs#L127), the Rust vector lookup in that file, and the uncached count plus page query in [`games.rs`](../../crates/kchess-core/src/store/games.rs#L791). The TypeScript comparison is the baseline at `f479f7c`; Rust is `8f58da7`.
