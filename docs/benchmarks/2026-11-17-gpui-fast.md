# GPUI Fast 0.1.16 against GPUI 0.3.12 with the KChess patches (2026-11-17)

**Status: evaluated, not adopted.** GPUI Kit 0.10.0 can build on GPUI Fast (Longbridge's fork
of Zed's GPUI) through its `gpui-fast` feature. This measures whether KChess should switch.

Builds: `main` at `dab85ab0` plus #243 (the voice bar no longer asks macOS about the microphone
on every frame, see below), on gpui-kit 0.10.0 with `vendor/gpui-pre` and every KChess patch,
against the same code with `gpui-kit/gpui-fast` turned on. GPUI Fast was copied out of the
registry with two stubs, `Window::zoom` (always 1) and `Window::set_zoom` (does nothing), since
the app calls the zoom patch it lacks. Release builds with `--features bench`,
`cargo xtask bench --runs 3 --seconds 20`, alternating run by run on an Apple Silicon Mac
(built-in display, 120 Hz, macOS 27.2.1); medians. No run was left out. Raw figures:
[`raw/gpui-fast-2026-11.json`](raw/gpui-fast-2026-11.json) (`suite_with_fix_243`; the other
keys are the runs before the fix and the bisection).

Both builds draw every frame the display asks for in every scenario: the analysis board holds
120 frames a second on both. GPUI Fast takes a third less main-thread time where the board
moves, which a player cannot see at 120 Hz but which is a few percent of CPU (and battery)
while analysing. It is three times slower on the openings grid, whose shell redraws ten times a
second, and opening a page costs the same.

## The first measurement was against a regression

Measured first against `main` as it was, GPUI Fast looked 11× faster on the board (0.8 against
9.5 ms a frame, `main` holding only about 92 of 120 frames a second with its main thread 90%
busy). On 2026-11-06 ([2026-11-06-motion.md](2026-11-06-motion.md)) the same scenarios drew in
1.4 ms. A bisection found #211: the voice bar read the microphone's state for its Privacy link on
every frame, and on macOS that asks the privacy service, about 6 ms each time. #243 fixes it.
GPUI Fast's retained subtrees had skipped the voice bar's redraw, so they hid the regression
rather than outperforming GPUI: with it fixed, the lead is the 1.3–1.5× above.

## What switching costs

GPUI Fast 0.1.16 is GPUI 0.3.12 (the release `vendor/gpui-pre` holds) plus about 19,000 lines
under `src/fast` and hooks in 44 upstream files. The app itself needed two changes to build:
GPUI Fast implements `IntoElement` for every `Element` (so `LiveRegion`'s own impl goes) and
`WindowBounds::centered` takes a display.

GPUI Fast already does what five of the KChess `gpui-pre` patches do, in its own way:

| KChess patch                                         | GPUI Fast                                   |
| ---------------------------------------------------- | ------------------------------------------- |
| Cached views inside a redrawn cached view are reused | `fast/splice.rs`, `fast/retained.rs`        |
| Replayed primitives keep their order, bounds once    | `fast/bounds_tree.rs`, `fast/scene.rs`      |
| Tab order sorted only when Tab asks                  | `fast/tab_stop.rs` (same idea)              |
| A reused view keeps its title-bar areas (Windows)    | `fast/retained.rs` replays them             |
| Only from the last frame (`drawn_in`)                | its own frame records                       |

These would have to be ported onto GPUI Fast's crates (`gpui-fast`, `gpui-fast-apple`,
`gpui-fast-macos`, `gpui-fast-windows`), or the feature is lost:

- **Interface size** (window zoom): `Window::zoom`/`set_zoom`, input scaling, IME bounds. A
  player-visible setting; the largest patch (`src/window.rs`, `interactive.rs`, `platform.rs`).
- **Icons drawn for their size** (`svg_renderer.rs`): without it icons blur on 1x displays.
- **Large clock glyphs drawn whole** (`gpui-pre-apple`): without it the 120 px clock loses half
  its colon.
- **Shaped text kept for a while** (`line_layout.rs`): GPUI Fast keeps one frame, like upstream.
  `pages-tour` shows no loss in page opening.
- **Typing a move into a notification** (`gpui-pre-macos`, `gpui-pre-windows`).
- Test-only: `show_window_menu`/`start_window_move` as no-ops and `Window::window_control_at`, which
  the end-to-end tests need.

The end-to-end tests were not run on GPUI Fast (they do not compile without the test-only
patches); `e2e::screens`, which checks every page redrawn from its cached frame pixel for pixel,
is what would show whether its retained drawing is correct for KChess.

Other facts for the decision:

- GPUI Fast is six weeks old (0.1.0 on 2026-10-06) with 17 releases since, about 180,000
  downloads, Apache-2.0, by Longbridge, who also make gpui-component and GPUI Kit. GPUI Kit 0.10
  pins it at `0.1.16`, so it moves with GPUI Kit.
- GPUI Kit keeps the upstream GPUI crates as build dependencies with the feature on, so both
  GPUIs compile: a clean build takes longer.
- Five patched crates would become four patched GPUI Fast crates; GPUI Fast is a larger and
  faster-moving base to re-apply patches on than GPUI's own releases.

## Recommendation

Do not switch now. With #243, KChess on GPUI already draws every frame on every screen measured;
GPUI Fast saves about a third of the drawing time on the board and loses three times on the
openings grid, for the price of porting five patches (one of them a player-visible setting)
onto a six-week-old fork and keeping them there. Measure again when a screen drops frames on
GPUI, or when GPUI Fast takes patches like the zoom upstream; the eval build is quick to
reproduce from this note (turn on `gpui-kit/gpui-fast`, patch `gpui-fast` with the two zoom
stubs, and make the two app changes above).

The bisection's lesson is the more useful one: the regression went unnoticed for nine days
because nothing runs the frame benchmark on `main`.
