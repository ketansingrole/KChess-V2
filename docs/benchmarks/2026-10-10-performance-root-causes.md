# Why the Rust migration has mixed performance results

This records the investigation before fixes. The subsequent implementation and verification are documented in [Performance fixes](2026-10-10-performance-fixes.md).

The migration improved CPU-heavy chess rules and the headless core's JavaScript memory footprint. It did not replace Electron, the Stockfish engine, SQLite, or the renderer. It also changed caching and data structures. Those facts explain why faster Rust computation does not translate into uniformly faster requests, lower desktop RSS, or smaller downloads.

This investigation compares TypeScript commit `f479f7ce10d7363df7132d616d8ad71b775ec7a7` with Rust commit `8f58da7f4d51371001e95d1c33cbd51ed9ad20c2` on the same Apple M5/macOS machine. It extends the [complete endpoint benchmark](2026-10-10-typescript-vs-rust.md) with isolated SQL, concurrent-network, large-tree and renderer-memory experiments. All profiles and servers were disposable. Product code was not changed. This is an endpoint comparison, not an experiment changing only the implementation language.

## What actually decreased

Visible packaged startup changed from 429 to 439 ms; normal page navigation stayed approximately equal. The strong regressions are resource overhead and specific service paths, rather than a general slowdown of the application. Idle process-tree RSS increased 41.8 MiB; active-analysis RSS increased 45.8 MiB. The unsigned ZIP increased 3.3%. These whole-app numbers coexist with core-worker peak JS heap falling from 83.0 to 8.2 MiB and peak RSS falling from 254.2 to 144.0 MiB.

Equivalent 34-ply PGN-tree import improved from 149.72 µs in TypeScript to 62.73 µs in renderer WASM and 40.29 µs in native Rust. Puzzle queries also improved. Those gains are real, but small rule operations cannot remove a second of SQL work or speed an unchanged external engine.

## Insights: the largest measured latency cost

The [SQL investigation](insights-hotspots.md) isolates the original per-row `strftime('%w', ..., 'localtime')` and `strftime('%H', ..., 'localtime')` expressions in [insights.rs](../../crates/kchess-core/src/store/insights.rs). On the original fixture both endpoint implementations spent almost the entire insights request in this SQL. This is predominantly an inherited database/calendar bottleneck, not slow Rust aggregation.

The [timezone probe](raw/insights-timezone-probe-2026-10.json) ran seven warm rounds in each of three fresh sequential processes. It retained the host zone (`Asia/Tokyo`) while varying how subprocesses identified it:

| Subprocess timezone       | Original two expressions | Combined expression | Distinct-first UTC-hour experiment |
| ------------------------- | -----------------------: | ------------------: | ---------------------------------: |
| Host default, `TZ` unset  |                 1,367 ms |              688 ms |                            22.0 ms |
| Explicit `Asia/Tokyo`     |                   979 ms |              494 ms |                            19.1 ms |
| Exact host zone-file path |                 1,155 ms |              578 ms |                            20.4 ms |

Full output hashes matched for all selected 20k modern rows and all 87,696 half-hour historical samples from 1948 through 1952, including Japan's historical DST. Default-process timed CPU was 2,218 ms user and 12,342 ms system, across all three timed queries. The large system-CPU component and sensitivity to timezone configuration support timezone-resolution overhead as a hypothesis; they do not prove an individual syscall or file lookup. Changing process-wide `TZ` alone is not an adequate product fix: host timezone changes and platform behavior must remain correct.

The corrected hour experiment first deduplicates 20k timestamps into 334 UTC-hour buckets, then formats those buckets. It demonstrates that repeated local conversion is the expensive work. It cannot be shipped unchanged for all zones: fractional offsets can put a local hour/day boundary inside a UTC hour, and historical transitions may occur within a bucket. A general solution needs transition-aware local conversion, carefully validated caching, or another representation preserving the user's local calendar. UTC-only bucketing changes behavior and is excluded.

First implement and benchmark the combined-expression candidate through the full insights API. Then evaluate a robust calendar conversion strategy against fractional-offset zones, DST gaps/folds, negative epochs, host timezone changes, ordering and aggregation parity. The 22 ms result measures SQL only and does not include full Rust aggregation or bridge/UI work.

## Port regressions with concrete explanations

In [accounts.rs](../../crates/kchess-core/src/lichess/accounts.rs:503), Rust checks the completed memory cache and immediately starts a new `load().await` on a miss. The historical TS service uses `profileCache.fetch`, which shares the pending fetch for that key. The [network burst raw](raw/network-inflight.json) checks actual server request counts and exact normalized outputs over three counterbalanced fresh-process pairs. Every same-key pair produced eight Rust requests and one TS request, with matching outputs; distinct-key controls produced eight requests each. Both implementations admit two concurrent HTTP requests, so the fixture's eight unshared requests require roughly four 100 ms waves. A replacement must preserve account epochs/logout protection, error semantics, cancellation ownership, and cleanup of failed pending entries. Coalescing should not serialize unrelated usernames or retry ambiguous mutations. The [network investigation](network-inflight-hotspot.md) records the details.

In [games.rs](../../crates/kchess-core/src/store/games.rs:791), Rust counts all matching games every time. The historical TS store caches totals by filter until data changes. Query-plan and isolated count/row measurements distinguish this from bridge overhead; page-row retrieval is already equal. Correct invalidation is essential for imports, inserts/replacements and deletions.

In [insights.rs](../../crates/kchess-core/src/store/insights.rs:80), opening-family grouping scans the vector for each row. TS uses a map. An index map alongside the existing vector preserves first-seen order and deterministic ties while removing the repeated scan. The 20k-label fixture is a stress test, and groups occurring only once are eventually filtered out; that filtering does not avoid the preceding grouping work.

## What the memory diagnostics establish

The [memory investigation](renderer-memory-hotspots.md) records two additional three-pair packaged studies. WASM instrumentation captures a 10,158,080-byte (9.69 MiB) rules linear buffer. It requires a controlled reload, which materially shifts RSS; its memory categories therefore cannot quantitatively account for the original startup delta. Buffer capacity does not measure resident pages or compiled WASM code.

The separate [GC diagnostic](raw/renderer-memory-gc.json) does not reload the page. It collects the renderer after each phase; later phases have been affected by those earlier collections and are not a replacement for ordinary startup measurements. Medians below use one observation per phase from each of three fresh launches per implementation:

| After explicit renderer GC | TS V8 used heap | Rust V8 used heap | TS renderer RSS | Rust renderer RSS |
| -------------------------- | --------------: | ----------------: | --------------: | ----------------: |
| Home                       |        8.96 MiB |          8.82 MiB |       152.4 MiB |         174.2 MiB |
| Analysis, engine off       |       12.17 MiB |         12.00 MiB |       196.2 MiB |         218.7 MiB |
| Analysis, engine active    |       13.85 MiB |         13.53 MiB |       209.3 MiB |         251.5 MiB |

Post-GC V8 heap capacity is also equal: 9.56 MiB Home, 13.13 MiB engine-off and 14.63 MiB active. Thus the residual renderer RSS difference persists with comparable retained JS heap and capacity. This rules out a large additional retained V8-object heap as the explanation for these sampled phases; it does not rule out a long-session leak. Native/WASM mappings, compiled code, allocator state and Chromium/embedder memory remain unresolved categories. CDP backing storage does not consistently include the tracked WASM buffer, so these figures must not be summed as an accounting identity.

Main-process GC was unavailable (`global.gc` absent), so no claim about post-GC main-process retention is made. Main `external` reporting was inconsistent across instrumented launches and is not used as an attribution. Precise next work is a mapping/allocation profile and a controlled component ablation that preserves functional startup, rather than adding forced GC to the product.

## Bridge, engine and package limits

The [large-tree study](architecture-hotspots.md) verifies equivalent output at 128, 384 and 768 plies. Full serialization sends the whole tree, but editing does not: an edit sends parent FEN/path and child-move information. Its 768-ply requests total about 7.8 KiB rather than the full 92.8 KiB tree. Deep-edit timing measures an existing-child reuse after warmup, not a fresh insertion every iteration. Native async dispatch differences were tiny relative to SQL. A wholesale bridge rewrite is therefore not the demonstrated highest-impact fix.

Stockfish is an external UCI process using the same search implementation in both revisions. Fixed search-time and cancellation measurements remained near parity. Infinite analysis intentionally uses its thread budget; after stopping, cumulative CPU grew only about 0.01–0.02 seconds over 9.5 seconds. Retaining an idle process is not evidence of continued search or a leak. An optional native engine comparison would need identical engine version, network, settings and output/strength criteria; no native-versus-WASM speedup was measured here.

The native addon already has fat LTO and one codegen unit. macOS removes local symbols at link time because post-link stripping has a documented dylib-loading problem. The renderer's configured 8 MiB WASM stack supports recursive trees up to 1,024 moves; reducing it requires deep-tree correctness verification. Generic stripping or shrinking stack size is not a justified free optimization.

The original network parity check also found a correctness issue: Rust TV channel output serializes `game_id` where the shared contract expects `gameId` ([watch.rs](../../crates/kchess-core/src/lichess/watch.rs:145)). TV timings are therefore ineligible for a like-for-like speed claim until compatibility is restored. A downstream visible failure was not established by this study.

## Scope and verification

Source findings are separated from candidate timings and unresolved allocation attribution. Results cover this macOS arm64 host, local deterministic data/network fixtures, and short packaged sessions. They do not establish Windows/Linux performance, production-network latency, long-session leaks, energy consumption, or gains after implementing these candidates. Companion raw artifacts preserve timings, request counts, output hashes and memory-category samples. No production optimization has been applied by this analysis.

All 13 benchmark scripts passed Node syntax checks. `pnpm run check:fast` passed formatting, lint, native build, type checks and all 82 unit suites / 845 tests after an unused diagnostic variable was removed. Both additional memory modes completed all six launches; the concurrent-network study completed all three pairs with exact output parity. No isolated benchmark app, engine or measurement-worker processes remained after verification. Full merge/release checks were not repeated because no product code or packaging configuration changed.
