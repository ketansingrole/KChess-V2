## 1. P2 — Overlapping failed autosaves make unacknowledged study content appear saved

Location: [analysis.ts:316](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/analysis.ts:316), [rollback:333](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/analysis.ts:333), [flush:337](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/analysis.ts:337).

**Reproduced with the real renderer stores and native library fixture.** Start from saved content C. Edit to A and start a delayed save. Edit to B and start a second save before A returns. Both saves fail. The first failure cannot roll back the shared `studyPgn` because B has replaced it; the second restores its `previous` value A, even though A never reached storage.

Return the board to A. `flushStudy()` resolves successfully without issuing another content write because it compares the board with that false saved marker. On recovery, the study store's strict quit retry persists its retained B intent. Another analysis flush still reports success while the board has A and the study has B. The diagnostic verifies that final divergence. The analysis recovery session may still preserve A; this is not evidence that every recovery copy disappears.

**Fix:** keep acknowledged content separate from pending content, track each write's identity, and let only successful acknowledgments advance the durable baseline. Build retries from the current document rather than an obsolete failed intent. Test A/B overlapping failures, return to A, successful strict flush and reopen. GPUI's analogous optimistic `study_pgn` rollback also deserves the same sequence test; it was not reproduced here.

## 2. P2 — Retrying an ambiguous study mutation creates duplicate documents

Location: [failure queue:176](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/studies.ts:176), [quit replay:145](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/studies.ts:145).

**Reproduced with the native library fixture and an injected lost reply.** Duplicate a study; let the backend commit the duplicate, then reject the caller's promise as though its connection closed before the acknowledgment arrived. The store queues every non-conflict error for retry. Strict quit flush sends the duplicate command again. The persisted study count goes from one to two after the original operation and to three after one retry.

The comment that these commands “never reached the core” is not established by a rejected promise. New-study creation, chapter addition and chapter duplication have the same non-idempotent boundary. This remains distinct from the previously fixed bug that retried an acknowledged command after local response adoption failed.

**Fix:** give create/duplicate/add operations stable operation IDs with transactional deduplication in the core. Until then, distinguish definite rejection from unknown commit status and reconcile unknown outcomes before replay. Preserve the commit → lost acknowledgment → quit retry sequence. The probe injects the transport outcome; it does not kill a running service.

## 3. P2 — Linked-study sync still accepts an import that appended no chapter

Location: [ignored import body:438](/Users/ketansingrole/git/kchess/crates/kchess-core/src/lichess/studies.rs:438), [success return:453](/Users/ketansingrole/git/kchess/crates/kchess-core/src/lichess/studies.rs:453), [UI completion:263](/Users/ketansingrole/git/kchess/apps/desktop/app/pages/studies.vue:263).

**Reproduced against a deterministic local HTTP fixture.** The standalone export path now validates the imported-chapter list. The linked-sync append loop still discards that body. Supply one baseline chapter and a local second chapter; answer the import with HTTP 200 and `{"chapters":[]}`; return only the original chapter on the final GET. `sync_lichess_study` returns `Done` with one chapter, despite the requested second chapter being absent.

The Electron caller marks the returned remote PGN as the cloud baseline and displays “Study uploaded.” The local second chapter remains available, but completion is falsely reported. The probe verifies response handling without asserting that this exact response occurs for every valid real-world upload or making a live Lichess mutation.

**Fix:** validate append acknowledgments using the same policy as standalone export, and reconcile the final remote result with the requested chapter count/content before marking the upload complete. Report partial completion accurately; retain local content and recovery state. Test zero-chapter and partial imports through both export entry points.

## 4. P2 — An initial review-status read overwrites newer streamed status

Location: [review.ts:74](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/review.ts:74), [lookup adoption:77](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/review.ts:77). GPUI has the same pattern in [reviews.rs:83](/Users/ketansingrole/git/kchess/apps/gpui/src/reviews.rs:83).

**Reproduced in the Electron review store.** `listen()` subscribes to status events and starts `reviewStatus()`. Hold an old lookup response, deliver a newer streamed status with three waiting reviews, then resolve the old lookup with zero waiting. The old reply replaces the newer state. Reversing the states can restore an obsolete running indicator after the last completion, with no later event guaranteed to correct it.

The store protects full-review and summary lookups using stream timestamps, but does not apply that protection to queue status.

**Fix:** capture a status-event generation before the lookup and adopt its result only if no newer event arrived. Apply it to every bootstrap/resynchronization read in both frontends. Test delayed idle and delayed running snapshots around terminal events.

## 5. P2 — Review queue state is not reconciled after core reconnection

Location: [Electron review listener:70](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/review.ts:70), [GPUI event handling:69](/Users/ketansingrole/git/kchess/apps/gpui/src/reviews.rs:69), [service bootstrap:380](/Users/ketansingrole/git/kchess-service/src/server.rs:380).

**Source-established; no live-service restart during a review was executed.** Both review stores fetch status only during initial setup and then consume future review events. Neither handles `core:reconnected`. The service's joining handshake supplies alert ownership, not a review-status snapshot. A client that misses a queue-completion event while disconnected can therefore retain an obsolete current review or waiting count after reconnecting. A fresh service similarly has no obligation to emit the status retained by the old frontend. Electron's `listening` flag prevents simply calling `listen()` again from refreshing it.

**Fix:** explicitly refresh authoritative review status and the pinned/incomplete review after reconnect. Reconcile interrupted work without silently replaying expensive review requests. Use the event-order protection from finding 4. Test disconnect → review completes on the surviving core → reconnect without another review event, plus service restart during review.

## 6. P3 — Shared view preferences stay at each frontend's startup snapshot

Location: [Electron load:28](/Users/ketansingrole/git/kchess/apps/desktop/app/composables/useViewPreference.ts:28), [existing refs:144](/Users/ketansingrole/git/kchess/apps/desktop/app/composables/useViewPreference.ts:144), [GPUI initialization:118](/Users/ketansingrole/git/kchess/apps/gpui/src/prefs.rs:118).

**Electron cache behavior reproduced; cross-client delivery gap source-established.** Preferences are stored centrally, but neither profile-refresh owner adopts remote preference changes or reloads preferences on reconnect. GPUI reads its global preference map once. Electron also reads once, and even explicitly calling `loadViewPreferences()` updates only the `saved` object: already-created refs still hold their old values.

For example, keep two apps open, change a tab in A, then navigate away and back in B. B can keep its old choice despite the shared profile storing A's newer choice. A new process reads the correct value. This affects the stated “open a page as it was left” cross-frontend behavior, rather than durable core storage.

**Fix:** define whether remote changes apply immediately or when a page next opens, and implement that policy in one preference owner per frontend. Refresh after reconnect, preserve pending local intents, and adopt remote values without echo-writing them. Test a remote update to both an instantiated preference and a page first opened after the update.

## Conditional robustness gaps and missing integration coverage

These helper failures were reproduced, but their full product trigger/impact was not established; they are not included in the six finding count.

- **GPUI incremental study adoption omits unknown IDs.** [StudyLibrary::apply:358](/Users/ketansingrole/git/kchess/apps/gpui/src/studies.rs:358) uses `filter_map` to discard IDs whose bodies are absent locally and from the incremental result. An extracted current-source helper probe confirms that order `[C, B, A]` plus bodies for A/C produces only C/A. Electron detects the missing bodies and requests a full reload; GPUI does not. Existing profile events and in-flight reloads may repair the omission, so a persistent omission needs a two-client scheduling reproduction. Add that sequence rather than assuming the helper result proves permanent UI loss.
- **The updater's cross-volume copy does not preserve bundle symlinks.** [copy_tree:648](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:648) treats every non-directory entry as a regular file. A directory symlink makes `fs::copy` fail; file symlinks are dereferenced. An extracted helper probe confirms the directory-symlink failure. This matters on the rename-failure/cross-filesystem branch for a bundle containing symlinks. The current GPUI package was not shown to contain such a bundle, and no signed installed app was replaced. Preserve link types/permissions, validate the destination bundle, and exercise a representative signed package across volumes.

The most valuable missing practices are acknowledged document baselines, transactional deduplication of durable commands, domain-level upload acknowledgments on every entry point, event-aware bootstrap reads, and complete reconnect reconciliation. Add failure-sequence tests crossing the frontend/transport/storage boundaries. The existing unit and helper suites are substantial, but their green result does not cover these sequences.
