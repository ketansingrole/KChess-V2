## 1. P1 — GPUI quits and installs updates even when saving failed

Locations: [core.rs:333](/Users/ketansingrole/git/kchess/apps/gpui/src/core.rs:333), [core.rs:369](/Users/ketansingrole/git/kchess/apps/gpui/src/core.rs:369), [analysis/mod.rs:440](/Users/ketansingrole/git/kchess/apps/gpui/src/pages/analysis/mod.rs:440), [analysis/mod.rs:885](/Users/ketansingrole/git/kchess/apps/gpui/src/pages/analysis/mod.rs:885).

**Source-established; no interactive disk-failure quit executed.** `BoxedSave` resolves to `()`, so the shutdown coordinator cannot distinguish a durable save from a failed attempt. The analysis quit callback explicitly discards the study result; session saving logs errors and returns success to the coordinator. The settings and study writer barriers also acknowledge reaching the end of the queue without propagating preceding write failures. `finish` then closes the core and runs the update callback unconditionally.

Concrete sequence: edit a study, lose service access or exhaust disk space, then quit. Both the study and recovery-session writes can fail, yet the app closes and may install the update. Waiting for requests to finish does not establish that the work was saved. Electron already has a useful equivalent in `QuitPreparation`, with retry/discard/cancel handling.

**Fix:** make flush results report persistence failures; retain failed intents and gate quit and update installation on successful persistence or an explicit discard choice. Test failure of both study and session writes, a failed settings write followed by a queue barrier, and retry after service recovery.

## 2. P1 — Explicit Windows update installation still starts before document flush

Locations: [updates UI:35](/Users/ketansingrole/git/kchess/apps/gpui/src/pages/settings/updates.rs:35), [Updates::install:1080](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:1080), [Windows apply:511](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:511).

**Source-established; Windows installer not executed.** The restart confirmation flushes only settings. `Updates::install` then calls `apply`, whose Windows arm immediately spawns NSIS with `--updated /S`. Only after `apply` returns does the UI call `cx.quit()`, which starts the document flush callbacks. The installed NSIS template waits briefly, requests application termination, and escalates to force-kill. A study/session save delayed beyond that interval can be interrupted.

The latest fix correctly moved _install-on-quit_ after the flushes, but the explicit “Restart and install” path does not use that ordering. macOS and AppImage replacements also precede the document flush on this path, although they do not have NSIS's forced-termination behavior.

**Fix:** have explicit restart use the same successful-flush-before-install transaction as quit. The installer/helper should wait for the old application to exit. Test with a blocked document save longer than the installer shutdown interval, and assert the installer cannot start early. Flushing settings alone is insufficient.

## 3. P2 — GPUI's settings queue loses a change reverted before the first acknowledgment

Locations: [settings.rs:268](/Users/ketansingrole/git/kchess/apps/gpui/src/settings.rs:268), [writer:191](/Users/ketansingrole/git/kchess/apps/gpui/src/settings.rs:191), [acknowledgment:211](/Users/ketansingrole/git/kchess/apps/gpui/src/settings.rs:211), [core merge:32](/Users/ketansingrole/git/kchess/crates/kchess-core/src/facade/settings.rs:32).

**Core behavior reproduced using the exact snapshot pairs the GPUI queue sends; GPUI scheduling itself not driven.** Each queued write captures its `stored` base when `save_now` runs, rather than after earlier writes finish. With sound initially on: turn it off and send save A; while A is pending, turn it back on and send save B. Both carry the original on-valued base. A stores off. B compares on against its stale on-valued base and declares that field unchanged, leaving off in storage. B's acknowledgment then adopts off into the form.

The new acknowledgment rebase handles edits during one pending save, but does not repair already captured subsequent requests. A slow first write plus two debounce intervals, or an immediate settings flush, exposes the sequence.

**Fix:** queue field intents relative to the preceding queued state, or serialize snapshot/base construction and rebase pending edits against each acknowledgment before sending the next request. Test on → off → on with both writes enqueued before A is acknowledged, including concurrent unrelated changes from another window.

## 4. P2 — Electron accepts snapshots that predate a completed local mutation

Locations: [profileSync.client.ts:29](/Users/ketansingrole/git/kchess/apps/desktop/app/plugins/profileSync.client.ts:29), [gameArchive.ts:155](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/gameArchive.ts:155), [kchess.ts:789](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/kchess.ts:789), [settingsPersistence.ts:101](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/kchess/settingsPersistence.ts:101).

**Reproduced in the real renderer plugin/store and settings composable.** The library read generation distinguishes one refresh from another, but not a refresh from an intervening local write. The archive guard protects a deletion only while it is pending. If an older library read returns after deletion has succeeded, the store is no longer busy and restores the deleted row. No deferred refresh was scheduled because the response did not arrive during the deletion. The database remains correctly deleted; the UI is stale.

Settings have the same ordering gap: begin a settings read, complete a local save, then receive the old read. `adoptStored` sees the form matching its newly acknowledged base and adopts the old value. Both the displayed settings and stored mirror now match the stale response, so the form is considered clean and does not repair itself.

**Fix:** invalidate reads on local mutations and acknowledgments, or carry authoritative snapshot revisions and reject older results. Use per-owner revisions so library refreshes can still preserve unrelated remote changes. Test responses delivered both during and after a deletion/save; current regressions cover the former, not the latter.

## 5. P2 — Electron skips recovery when the online UI was idle

Locations: [kchess.ts:871](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/kchess.ts:871), [challenges.ts:101](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/challenges.ts:101), [fresh core state:203](/Users/ketansingrole/git/kchess/crates/kchess-core/src/lichess/online/state.rs:203), [assistance gate:588](/Users/ketansingrole/git/kchess/crates/kchess-core/src/facade.rs:588).

**Renderer registration behavior and fresh-core assistance gate reproduced separately.** The new reconnect callback returns unless the phase is playing, seeking or disconnected. Restart the service while the Electron window is idle or showing a finished game: no `resumeOnline` runs. A new core starts with `recovery_unverified = true`, which blocks computer moves, analysis and review until recovery establishes there is no live game. The local diagnostic confirmed a fresh core rejects a computer request before resume and returns a legal move after resume.

The idle challenge stream also has state in the old core. `useChallengeStore.start()` runs once and its lobby-account watcher fires only when that value changes; reconnect does not restore `stayConnected` or reread challenges. Resuming an active game alone would not restore this lobby preference either. A service restart can therefore stop incoming challenges/pairings despite an unchanged selected account.

**Fix:** bootstrap online verification and restore lobby intent on every core reconnect, independent of the previous board phase. Keep assistance unavailable until verification finishes and never replay ambiguous moves. Test idle, finished, active, and challenge-receiving windows against a fresh service. The existing test explicitly expects idle recovery to be skipped and should change.

## 6. P2 — Installation exclusivity is local to one GPUI process

Locations: [installation:1058](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:1058), [workspace lock:735](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:735), [replacement:573](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:573), [startup cleanup:787](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:787).

**Source-established; concurrent real installations not executed.** `Installing` and `staged.take()` prevent duplicate application in one entity. The workspace locks protect separate download folders, but no lock owns the installed application path. Two GPUI processes from the same installation can still apply updates concurrently. They share `.APP.new`/`.APP-old` paths, and each replacement starts by removing the incoming path. A second process starting during installation also calls `tidy` unconditionally, which can delete the first process's incoming copy.

On AppImage, one process can remove another's incoming file before rename. On macOS, competing replacements can interfere with the exchange or fallback backup. Private download staging fixes the earlier download collision, not these destination-side races.

**Fix:** hold an interprocess lock keyed to the canonical installation through preparation, replacement and cleanup. Startup cleanup must consult the same owner. Test two processes sharing one installation and startup while a replacement is paused after creating the destination-side incoming artifact.

## 7. P2 — Detached .deb installation outlives the lock protecting its package

Locations: [apply_on_quit:808](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:808), [clear_stopped:775](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:775).

**Source-established; no privileged package operation executed.** Install-on-quit spawns a shell that waits for the app PID to exit, then invokes `pkexec dpkg -i` with the staged pathname. The workspace lock belongs to the exiting app, not that helper. Once the app exits, a new GPUI process can acquire that lock and delete the old workspace. If the helper has not yet opened the .deb, or the permission dialog is still waiting for authorization, the package disappears before `dpkg` opens it. The detached command's output is discarded, so the failed installation has no visible recovery owner.

**Fix:** transfer artifact ownership and a lock to the installer helper until package-manager completion. Coordinate cleanup with that owner and record its outcome for the next launch. Test immediate relaunch while authorization is pending; assert the package remains available until installation finishes or cancellation is recorded.

## 8. P2 — The macOS non-exchange fallback still has an unrecoverable crash window

Locations: [updates.rs:583](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:583), [fallback:591](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:591), [cleanup:793](/Users/ketansingrole/git/kchess/apps/gpui/src/updates.rs:793).

**Conditional source-established defect; no installed app interrupted.** The new destination-side staging fixes partial cross-volume copies, and successful atomic exchange removes the normal crash gap. However, any exchange error enters a two-rename fallback: move the installed app to `.app-old`, then move incoming to the normal launch path. A crash between those renames leaves the launch path absent. Rollback runs only when the second rename returns an error, not after process termination. There is no external recovery owner; cleanup deletes the old backup rather than interpreting an interrupted transaction.

**Fix:** if atomic exchange is unavailable, stop with a manual-update error while the old app remains installed, or use an independently recoverable transaction/helper. Test the exchange-error branch with injected termination after the first rename. The current interrupted-copy test stops before the installed app is touched and does not cover this branch.

## 9. P2 — GPUI account reads are not invalidated by local account changes

Locations: [accounts.rs:108](/Users/ketansingrole/git/kchess/apps/gpui/src/accounts.rs:108), [OAuth result:161](/Users/ketansingrole/git/kchess/apps/gpui/src/accounts.rs:161), [sync result:205](/Users/ketansingrole/git/kchess/apps/gpui/src/accounts.rs:205).

**Source-established; UI response ordering not exercised.** The new `Reads` guard orders refreshes, but this module never calls `reads.edited()` when it adopts a local connect/sync result. Start a profile refresh; let its `loadData` snapshot reflect old accounts while its usage request is delayed; complete an OAuth refresh or sync and adopt the newer `data`; then let the old refresh finish. It still passes `Answer::Show` and replaces the newer account data. Local profile events are deliberately ignored, so they do not guarantee a subsequent correcting read. A refreshed login to an already-connected account also returns before starting the new-account sync path.

**Fix:** invalidate account reads when local mutations start/commit, and refresh again if necessary; use the same generation/revision ownership for data and usage. Test a delayed refresh finishing after successful OAuth, logout/removal, and sync. Read/read reversal alone does not cover this.
