## 1. P2 — Quitting an untouched window overwrites another client's saved game session

Locations: [unconditional session write](/Users/ketansingrole/git/kchess/apps/desktop/app/utils/library.ts:162), [quit registration](/Users/ketansingrole/git/kchess/apps/desktop/app/utils/library.ts:171), [ignored session changes](/Users/ketansingrole/git/kchess/apps/desktop/app/plugins/profileSync.client.ts:14).

**Reproduced with the real local-game store and native library storage.** A loads an empty local session and never plays a move. B saves a valid local session containing `e2e4` to the shared core. A runs `flushSavedDocuments()`, as normal quit preparation does. The persisted local session changes back to an empty move list.

`persistSession` writes on every quit, unload and disposal without checking whether this owner changed its document. Other clients' `sessions` notifications are deliberately ignored. `initialLibrary()` is a startup snapshot; opening a page later does not itself fetch current session data. The core's document writer accepts the stale replacement without a baseline check. This is durable loss of the resume position, not proof that an independently archived game disappears. The generic persistence helper also serves analysis and computer sessions; those full product sequences were not separately reproduced.

**Fix:** retain the last acknowledged session and avoid writing unchanged sessions at quit. Refresh sessions before first use and define conflict/ownership behavior when both clients edit one session; use a revision or compare-and-swap base to reject stale replacements. Preserve B's progress while leaving A's active board alone. Test idle A → B saves → A quits → reopen, plus simultaneous edits and stale first page opening.

## 2. P2 — A puzzle download completed elsewhere leaves this client permanently busy

Locations: [progress listener](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/puzzles.ts:286), [busy calculation](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/puzzles.ts:315), [card branches](/Users/ketansingrole/git/kchess/apps/desktop/app/components/PuzzleDbCard.vue:43).

**Reproduced in the puzzle store with injected authoritative status/progress.** Open this client's card while another client is downloading: its status contains `busy: true`. Finish the download and deliver the terminal `done` event. The listener changes only `dbProgress`; `db.busy` remains true, so `dbBusy` remains true. The card keeps the progress/Cancel branch and hides its normal refresh/delete controls. Explicitly calling `refreshDb()` restores the correct idle state, but the terminal-event path does not do so.

Only the client that called `installDb()` gets that method's final status refresh. The same observer gap applies to cancellation/failure. A client loaded before someone else's installation/deletion can also retain obsolete installed/count information: the profile-sync plugin ignores the `puzzles` area. No real 300 MB download was performed.

**Fix:** reconcile authoritative database status for terminal progress events, external puzzle changes and core reconnection. Subscribe before the initial status read, guard overlapping reads, and account for the terminal event potentially preceding the service clearing its running flag. Clean up the progress subscription with its store owner. Test the initiating and observing clients through success, failure, cancel and reconnect.

## 3. P2 — Puzzle history can cache an obsolete snapshot indefinitely

Locations: [attempt invalidation](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/puzzles.ts:81), [history cache](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/puzzles.ts:133), [profile area routing](/Users/ketansingrole/git/kchess/apps/desktop/app/plugins/profileSync.client.ts:17).

**Two sequences reproduced in the real puzzle store.**

- Start a history read returning the old totals and delay its reply. Complete/log a new puzzle attempt; its acknowledgment updates progress and marks history stale. Deliver the old history reply. `loadHistory()` adopts it and sets `historyStale = false`, consuming the newer invalidation. Calling `loadHistory()` again returns the old cache without issuing a read. The probe observes training progress at one attempt while history stays at zero.
- Cache history, then deliver another client's `profile:changed` event for `puzzles`. The plugin does nothing for this area. Reopening History calls `loadHistory()` but its freshness shortcut still returns the obsolete cache. Reconnection does not invalidate this cache either.

The records remain in the backend; the displayed history/totals are stale until another local attempt or app restart happens to invalidate them. Separately, the cache has no calendar-day key, so its Today totals and streak calculations also warrant a midnight regression.

**Fix:** track an invalidation generation and the local day. Adopt a history result as current only if its generation/day still match. Invalidate or refresh puzzle progress/history on external puzzle changes and reconnection. Add regressions for attempt acknowledgment during a read, external attempts while History is closed, and midnight rollover.

## 4. P3 — A late repertoire acknowledgment restores counters already cleared successfully

Locations: [record acknowledgment](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/studies.ts:272), [clear acknowledgment](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/studies.ts:281).

**Reproduced with the real study store and native library, delaying one acknowledgment after its storage commit.** Record a miss and hold its reply. Clear misses and allow that operation to finish. Both the core and renderer now contain no misses. Release the older record reply: its full-map assignment restores the cleared counter in the renderer, although storage remains empty. No corrective reload is scheduled. The opening trainer uses this map to weight the next lines, so it continues training against stale weaknesses.

`libraryWrites` protects external library snapshots but does not order these mutation responses. This probe injects response delay; it does not establish how frequently the production service schedules replies in this order.

**Fix:** serialize repertoire mutations through one owner, or attach revisions to responses and reject obsolete snapshots. Preserve optimistic changes until their own acknowledgments and reconcile the final authoritative map. Test record → clear → late record reply, successive records and independent keys.

## 5. P2 — Switching tournament accounts leaves the previous account's personal controls visible

Locations: [watched identity](/Users/ketansingrole/git/kchess/apps/desktop/app/components/TournamentEvent.vue:27), [membership derived from old `me`](/Users/ketansingrole/git/kchess/apps/desktop/app/components/TournamentEvent.vue:39), [detail reply adoption](/Users/ketansingrole/git/kchess/apps/desktop/app/stores/tournaments.ts:87).

**Reproduced by mounting the real tournament component.** Load an arena for Alice with `me.withdraw = false` and Alice's ongoing game. Switch the active account to Bob. The component still shows “You are in” and “Go to your game,” and sends no new detail request. Its watcher keys only the event ID/system; its `me` snapshot is not bound to an account. The buttons subsequently use the current active account, so Alice's game ID is handed to `openOngoing` as Bob, and Pause/Withdraw targets Bob despite being displayed from Alice's membership.

Normal polling may repair this after the next successful 15-second refresh; failure or offline status extends the mismatch. A delayed detail response for Alice can also be adopted after the switch because the store checks only its request counter, not account identity.

**Fix:** include the account in detail-request identity, clear personal fields immediately on account changes and reload the open event. Guard adoption against account changes, and bind actions to the account represented by the displayed details. Test delayed old-account replies, a switch while joined, and offline account switches.
